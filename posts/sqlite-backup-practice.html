cp 出来的数据库备份，打开是坏的

2026-11-26 · sqlite备份 · 约 3 分钟

SQLite 最大的卖点是一个文件就是整个数据库，于是很多人（包括以前的我）得出一个危险的结论：备份嘛，cp 一下就完了。直到某天恢复时打开报错 database disk image is malformed，我才去补这一课。

SQLite 最大的卖点是一个文件就是整个数据库，于是很多人（包括以前的我）得出一个危险的结论：备份嘛，cp 一下就完了。直到某天恢复时打开报错 database disk image is malformed，我才去补这一课。

🐳 单文件不是护身符

SQLite 的写入不是原子的文件级操作。写事务进行到一半时，页缓存、journal、WAL 都处在中间状态，这时候 cp 出来的快照，运气好丢最近几个事务，运气差页结构不一致，整个库就是坏的。

更麻烦的是你根本不知道自己运气好不好——损坏往往在恢复那天才被发现，而距离备份可能已经过去很久。

结论其实很简单：确认没有任何连接的静态库，随便 cp；正在写入的在线库，永远别直接 cp。

🐳 正确姿势就两行

官方给的路子很清楚：在线备份 API，或者 VACUUM INTO。后者特别适合脚本，一句 SQL 出一个一致的快照：

sqlite3 app.db "VACUUM INTO '/backup/app-2026-11-26.db'"
sqlite3 /backup/app-2026-11-26.db "PRAGMA integrity_check;"

我的日常方案就三步：定时任务每天 VACUUM INTO 一份，跑一次完整性校验，然后 rsync 推到 NAS 异地存。本地留十四天，旧的清掉。

程序里则用 backup 接口，src.backup(dst) 三行搞定，逐页拷贝，自带一致性保证。

🐳 WAL 三件套的小脾气

开了 WAL 模式之后，.db 旁边还有 -wal、-shm 两个伴生文件，事务先写在 wal 里，之后才合并回主文件。这带来两个坑：

一是迁移时不能只拷 .db 把 wal 扔在原地——先执行 PRAGMA wal_checkpoint(TRUNCATE); 合并完再拷，否则最近的事务全在 wal 里。

二是 WAL 在网络文件系统上有已知的锁问题，数据库文件放本地盘，别放在挂载的网盘上跑。

💡 一点观察

SQLite 的「轻」很容易变成「从不备份」。判断一个库靠不靠谱，看的从来不是它多小巧，而是丢掉之后多久能回来。
