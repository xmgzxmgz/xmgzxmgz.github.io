从 CHANGELOG 到 Release：一条管线的故事

2026-11-24 · CI GitHub Actions · 约 2 分钟

两个构建 job 都会更新 release，默认正文是空串，谁后跑谁清空。修法：正文只在一个地方写，写在最后。

上一篇写了 CHANGELOG 本身的教训，这篇讲把 CHANGELOG 变成 Release 正文的那条管线，以及中间踩过的竞态。

🏗️ 原来的流程长这样

push tag v*
  ├─ job: build-macos   → tauri-action → 创建 release（tagName/releaseName）
  └─ job: build-windows → tauri-action → 找到 release，追加安装包

问题在于 tauri-action 每次都会调一次「更新 release」的接口，而正文参数不传的话默认是空串。两个 job 各更新一次，后跑的那个把正文写成空串。

🔧 收口 job

修法是不碰那两个 job，在最后加一个 finalize-release：

finalize-release:
  needs: [build-macos, build-windows]
  steps:
    - 从 CHANGELOG.md 抽取本版本段落 → .release-notes.md
    - gh release edit --notes-file .release-notes.md

三个细节：

  • 抽不到条目时不失败，写一段兜底正文并打 warning——别把「忘了写 CHANGELOG」变成「构建失败」
  • 两个平台都挂了、release 根本不存在时，跳过写入，同样只打 warning
  • 脚本里注释写清楚「为什么在这里写」——三个月后自己会问

💡 通用原则

多个写者 + 一个会被整体覆盖的字段 = 竞态。解法永远是把写收敛到一个点，并且放在最后。

这 61 行 diff 全是新增，没改任何现有步骤——对已经跑了几十次的流程做手术，新增比修改安全得多。
