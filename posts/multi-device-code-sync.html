多设备同步，我最后选了最无聊的方案

2026-11-27 · git工作流 · 约 3 分钟

我折腾过多设备代码同步的花活，最后活下来的方案无聊到没什么好写的：代码走 git，配置走 dotfiles，大文件走网盘。

我折腾过多设备代码同步的花活，最后活下来的方案无聊到没什么好写的：代码走 git，配置走 dotfiles，大文件走网盘。

无聊，但它没坏过。

🐳 云盘碰不得仓库

踩过的最大的坑，是把项目目录直接丢进同步盘里图省事。

两台机器同时改，同步盘的处理方式很直接——生成「冲突副本」。普通文件冲突副本顶多乱一点，但落在仓库的内部对象上，整个仓库直接报损坏。版本管理工具的对象存储根本不是为并发文件同步设计的，这件事我付出过一次重建仓库的代价才真正记住。

结论简单粗暴：源代码只走 git，远程仓库是唯一真相源。云盘想参与，可以，但请去管它该管的东西。

🐳 四层各走各的

想通分层之后，方案其实就定了，每类内容走各自的通道：

  • 代码：git 加远程仓库，可合并、冲突可见；
  • 配置：单独一个 dotfiles 仓库，用 chezmoi 或 stow 管理，新机器一条命令还原；
  • 大文件：数据集、媒体这类二进制，交给网盘或家里的 NAS，它们不适合进版本库；
  • 凭据：密码管理器或加密方案，任何明文同步通道都是泄露源，这一层永不参与同步。

配置这块多说一句。chezmoi 能按主机和系统做条件区分，一台 Mac 一台 Linux 也能共用一份配置，代价是要学一点模板语法。轻量需求用 stow 也完全够，我的建议是从简单的开始。

🐳 纪律比工具重要

方案定了之后，真正防冲突的是三条纪律：

换到一台设备的第一个动作是拉取，把昨天收工的内容带下来；收工必推送，本地独占的时间越长，风险越大；提交小步走，一个逻辑改动一个提交，冲突粒度小到肉眼可解。

git pull --rebase   # 开工第一件事
git push            # 收工最后一件

再补两个小技巧：两台设备尽量各干各的事、各自开分支，避免同一个分支双头改；长期要离开某台机器前，用 git 的打包命令导出一个单文件快照带走，所有历史都在里面，算作兜底。

💡 一点观察

同步方案的花活多半死于「多了一个会自己动的环节」。git 这种每一步都要我亲手确认的笨办法，反而因为它什么都不会自作主张而最可靠。工具的无聊，有时候就是它的优点。
