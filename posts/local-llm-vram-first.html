本地跑大模型前，先做一道乘法题

2026-11-25 · 本地模型显存 · 约 3 分钟

想本地跑个大模型，多数人的第一步是打开模型列表开始下载。我的第一步也是——直到模型在我那台机器上跑得像慢动作回放，才回头补上这道本该最先做的乘法题。

想本地跑个大模型，多数人的第一步是打开模型列表开始下载。我的第一步也是——直到模型在我那台机器上跑得像慢动作回放，才回头补上这道本该最先做的乘法题。

🧮 一道乘法题

显存需求其实就一个公式：参数量 × 每个 token 占的字节数，后者由量化等级决定。

Q4 量化下有个很好记的速算：每十亿参数约等于 0.6 到 0.7 GB。所以 7B 约占 5GB，14B 约占 9GB，32B 约占 19GB，70B 直接奔 40GB 起步，单卡基本告别。

这道题的价值在于「下载之前就知道行不行」。8G 显存跑 7B 的 Q4 很从容，14B 就得掂量，32B 想都别想——不用下完 19GB 才发现。

🎚️ 卡线时的两种减法

量化等级里，Q4 是速度与质量的甜点；Q8 接近无损，但显存几乎翻倍，再往上意义不大。

容易漏算的是上下文。KV 缓存要另占一块显存，32K 的上下文轻轻松松再吃 1 到 4GB。显存刚好卡线的机器，出路就两条：降一档量化，或者砍上下文长度。

写着写着，思路清楚了——显存预算从来不是「能不能跑」的是非题，而是参数量、量化、上下文三者互相让步的谈判桌。

🧭 装好之后干什么

工具走双轨就够。Ollama 做后端：命令行加 OpenAI 兼容的本地 API，接什么都即插即用。LM Studio 做体验：图形界面里拖一拖，装不下的层可以卸到内存。

ollama pull qwen3:8b
ollama run qwen3:8b
# 本地 OpenAI 兼容 API，默认端口 11434

但比工具更重要的是定位。本地模型的强项是三件事：隐私敏感的东西不出机器；离线环境里它是唯一选项；批量打标这类低价值任务边际成本为零。弱项也很清楚——顶尖推理和长文创作，本地模型与云端旗舰的差距肉眼可见。

💡 一点观察

所以最终的答案不是「本地还是云端」，而是路由：什么任务放哪里。这和开头那道乘法题是同一件事——先算清楚，再决定钱和卡花在哪。
