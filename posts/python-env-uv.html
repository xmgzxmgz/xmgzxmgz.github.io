四个工具的活，现在一个 uv 干完

2026-11-27 · Pythonuv · 约 2 分钟

我搭一个 Python 项目的老流程，要用到四个工具：管版本一个、建环境一个、装依赖一个、装命令行工具又一个。直到换了 uv，才发现这四件事其实是一件事。

速度快是 uv 最初吸引我的原因，但用下来让我留下的是别的东西——锁文件带来的可复现。

🐳 四合一

先数一下老一套各有各的痛点：版本管理工具装解释器，虚拟环境要建完再手动激活，依赖文件写着写着就和实际装出来的对不上，全局装的命令行工具还会互相打架。

uv 把这四件事收进一个命令：

uv init myproj && cd myproj
uv add requests rich   # 依赖自动记进项目文件
uv run main.py         # 直接跑，无需激活
uv tool install ruff   # 命令行工具也是它管

最舒服的是 uv run：不用再想「激活了吗」，脚本自动跑在项目自己的环境里。依赖装到全局去了这种经典事故，第一步永远是看命令指向哪里——这个排障本能现在用上的机会少多了。

🐳 锁文件才是主角

快只是体验，锁文件才是可复现的保证。

uv.lock 记录的是整个依赖树被解析之后的精确状态。应用项目里我把它提交进版本库——今天能跑的代码，半年后在任何一台机器上装出来的是同一套东西。CI 里也用锁文件复现，不猜版本。

但有个细节值得分情况：如果你发布的是给别人用的库，锁文件反而不该提交，只提交声明了版本范围的配置文件，把依赖组合的选择权留给使用者。

老项目迁移也简单，把老的依赖清单批量导入一遍，校验锁文件之后，旧文件就可以留档退役了。

🐳 原理还是要懂的

工具再省心，隔离的原理还是值得懂一遍，不然出问题会两眼一抹黑。

激活虚拟环境，本质只是把那个环境的目录放进 PATH，让命令指向环境内的解释器——懂了这一句，大部分环境灵异事件都能自己排障。剩下的高频坑也不神秘：编辑器没指向项目环境、个别包在过深的路径下装不上、二进制依赖和解释器版本不匹配，以及系统自带的 Python 不要硬灌。

💡 一点观察

从四个工具到一个工具，省下的不只是学习成本，更省的是「环境到底是谁说了算」的犹豫。可复现这件事平时没有存在感，出问题的时候，它是唯一的救生索。
