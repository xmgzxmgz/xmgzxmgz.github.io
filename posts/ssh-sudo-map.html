sudo cd 都会报错，我给 NAS 画了张权限地图

2026-11-26 · NASSSH · 约 3 分钟

第一次 SSH 进 NAS，我信心满满敲了一行 sudo echo x >> /root/test，回车，Permission denied。

第一次 SSH 进 NAS，我信心满满敲了一行 sudo echo x >> /root/test，回车，Permission denied。

明明带了 sudo。那一刻我意识到，这台机器的权限模型跟直觉不一样，得老老实实画张地图。

🗺️ 界面上的名字，都是别名

第一课是路径。前端界面里的「SATA 存储」「个人空间」，在 SSH 里根本不存在，那只是展示层的别名；真实路径藏在 zfuse 联合挂载点下，按物理卷和用户 ID 组织。

更要命的是权限：这个挂载点是以 root 身份挂的，普通 SSH 用户对它只有读权限，想改文件必须 sudo。

这张地图的第一层就是：界面别名 → 挂载点 → 真实路径。改配置前先 ls -la 确认站在哪，别被软链骗了。

🔑 sudo 的几个反直觉细节

用熟之后，我踩过的坑可以凑一张清单。

密码喂法：非交互场景用 sudo -S 从 stdin 喂密码，脚本才不会卡住。

sudo cd 不存在。sudo 是按命令授权的，cd 是 shell 内建命令，sudo 根本找不到它。想看哪就 sudo ls 加绝对路径。

重定向逃逸，就是开头那次的元凶：sudo echo x >> file 里，>> 是当前 shell 执行的，而当前 shell 没有写那个目录的权限。sudo 只保护了 echo，没保护重定向。正确写法是把整条命令包进 root 的 shell：

sudo bash -c "echo x >> /root/test"
# 或者借道 tee
echo x | sudo tee -a /root/test

SFTP 直写 root 拥有的文件也会失败，我的流程是先传到自己的 home，再 sudo cp 到位。

🗑️ 删除这件事，永远留后路

这张地图上最重要的一条红线：删文件不走 rm，走回收站路径。移到回收站目录，前端还能看到、还能反悔，这是数据安全的最后一道缓冲。

另外：SSH 端口不是默认的 22；系统升级可能重置挂载结构，重要改动备份到 home 并记笔记。

回头看，这些限制其实都指向同一个设计哲学：默认给你的，是刚好够用的权限。

💡 一点观察

最小放行不是麻烦，是 sane 默认。只读的挂载、按命令授权的 sudo、强制走回收站的删除，每一层都在替「手滑的我」兜底。权限地图画清楚之后，剩下的就是别跟系统对着干。
