API 账单翻倍那天，我重新算了 token 的账

2026-11-25 · 成本模型选型 · 约 2 分钟

账单这东西，涨的时候没人提前打招呼。与其对着月底的数字叹气，不如把它当成一个工程问题：先拆结构，再排杠杆。

🧾 账单的解剖

token 计费的结构比想象中立体。第一层：输入单价通常只有输出的四分之一到八分之一——所以省输入不如控输出，方向别搞反。

第二层是容易被忽略的乘法因子：多轮对话每轮都会把历史完整重发一遍。聊到第二十轮，前面十九轮的 token 全在陪跑，轮数越多乘得越狠。

第三层是隐性成本：失败重试、失控变长的轮次、Agent 循环里不知不觉烧掉的调用。它们不出现在单价格式里，但都真实扣钱。

📉 最大的杠杆是换模型

拿文档问答算过一笔账：输入 8K、输出 1K，旗舰模型一次约四美分，二线模型三厘，差 13 倍。一天 200 次，一个月下来就是几十美金的差距。

def cost(in_t, out_t, in_p, out_p):
    return in_t / 1e6 * in_p + out_t / 1e6 * out_p

# 输入 $3/M、输出 $15/M 的旗舰
print(cost(8000, 1000, 3, 15))    # 0.039
# 输入 $0.3/M、输出 $0.6/M 的二线
print(cost(8000, 1000, 0.3, 0.6)) # 0.003

判断口诀只有一句：先问「这任务答错了会怎样」。分类打标答错无所谓，上旗舰是纯浪费；复杂推理用二线，返工的成本比省下的钱贵。按风险分配预算，而不是按虚荣心。

✂️ 小钱也要拧

换完模型，剩下的杠杆按效力排：上下文瘦身，检索结果重排后只留前三条，历史对话定期折叠成摘要，输入减半成本减半；输出控制，提示里写明「最多两百字」「只输出 JSON」——输出 token 是最贵的 token；缓存，长系统提示做成固定前缀，命中部分折扣很可观；批处理，非实时任务走批处理接口，普遍半价。

💡 一点观察

算完发现，成本问题说到底还是个路由问题：给每个任务配刚好够用的模型。之前写个人 Agent 设计时提过分层，这次不过是把钱也分了层。
