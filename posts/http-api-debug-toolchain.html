你以为的请求，和实际发出的请求

2026-11-26 · api调试 · 约 3 分钟

接口在文档里一切正常，curl 一打也通，一到浏览器里就是 401。这种时候最容易怀疑人生——后端说接口没问题，前端说代码没改过，双方都没说谎。

真相通常很朴素：你以为发出去的请求，和实际发出的请求，不是同一个。

🧰 工具是分层的

我的工具链慢慢收敛成三层，各干各的活。

curl 是底座。可复现、可粘给别人、能进 CI 脚本。怀疑接口本身有没有问题时，先绕开一切壳子，用它直接打一遍：

curl -v https://api.example.com/v1/items \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"page":1}' | python -m json.tool

-v 是精髓，握手、证书、响应头全在，证书问题一眼现形。

图形客户端管管理。接口多了以后，collection 和环境变量比命令行顺手，多套环境切换也不用满世界改地址。

抓包管真相。浏览器 DevTools 的 Network 面板、或 mitmproxy，负责回答那个终极问题：客户端到底发了什么。

🕵️ 对照是最快的路径

所以那个 401 的悬案，解法就是把两个请求摆在一起看：DevTools 里实际发出的，和你 curl 里预期发出的，逐字段对照。

我经历过的案例，九成在对照后五分钟内破案：少了一个头，Content-Type 写错，或者 body 外面多包了一层。都不是什么高深的 bug，只是没人把两个请求并排放过。

养成的习惯是：调不通时，第一动作不是改代码，是打开对照。

🔑 事故常在环境变量

还有几类经典事故，工具本身没错，错在环境。

图形客户端里缓存着上个月的旧 token，刷新了也不重贴——401 事故的头号来源。所以环境隔离必须彻底：地址、凭证全走环境变量，dev、test、prod 三套配置，切换环境等于切配置，永远不手改。

另外记住一条免责判定：curl 通而浏览器不通，不一定是后端的锅。CORS 是浏览器才有的行为，先去看网关有没有给响应头，别急着在后端翻日志。

对了，抓包工具用完记得恢复系统代理。「断网玄学」的一大半，是代理设置残留在作祟。

💡 一点观察

调试 API 的核心能力不是记住多少工具，而是始终保持一个怀疑：我看到的，是不是我以为的那个请求。把「实际发生的事」和「以为发生的事」对齐，大部分玄学自动消失。
