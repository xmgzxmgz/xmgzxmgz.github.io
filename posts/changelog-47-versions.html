47 个版本的 CHANGELOG 教我的事

2026-11-24 · 工程习惯 CHANGELOG · 约 2 分钟

写了 47 个版本的 CHANGELOG，release 正文却一直是空的。排查下来根因只有一个，但顺手想明白了几件更重要的事。

我的旗舰项目到现在写了 47 个版本的 CHANGELOG。每一条都按「现象 → 真因 → 修法 → 验证」的结构写，连逐 tab 的验证结果都记了。但直到上周我才发现一个尴尬的事实：GitHub 的 Release 页面上，连续三十多个版本的正文是空的。

🔍 根因只有一个，但很隐蔽

不是忘了写，是工作流的结构问题：发布工作流里 macOS 和 Windows 两个 job 都会去更新 release，而「正文」这个参数有默认值——空字符串。两个 job 谁后跑完，谁就把正文覆盖成空。即使哪次手动写了，下一次构建也会被清掉。

修法说破了不值钱：正文只在一个地方写，而且写在流程最后。我加了一个收尾 job，等两个平台都跑完，从 CHANGELOG 里抽出对应版本段落统一写入。

✂️ 自动摘要失败了，这不是坏事

我本来想让脚本自动从条目里抽摘要（取加粗小标题、按关键词分类），结果抽出来的是「用户截图实录」「bump 0.6.31 → 0.6.32」这种过程描述。因为我的写法是叙事结构，要点藏在内层缩进里，正则切不出结论。

最后的约定是：脚本负责搬运，人负责结论。写 CHANGELOG 时顺手在标题下加一行一句话摘要，Release 就有一个正常人能读懂的开头；不加也不坏，回退用标题。

💡 这 47 个版本真正教我的

回看这些记录，最值钱的不是「修了什么」，而是每次都写下来的「真因」。有几个 bug 的第一直觉判断是完全错的（比如一个「硬件不支持」的结论，两个月后发现是 APDU 长度限制、换条路就通了）。如果没有真因记录，这些弯路会被忘掉，然后以另一种形式再走一遍。

CHANGELOG 不是给用户看的日志，是给三个月后的自己看的破案笔记。
