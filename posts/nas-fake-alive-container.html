docker ps 说它活着

2026-11-25 · dockernas · 约 2 分钟

周日晚上的意外就这么来了：手机上订阅刷不出来，第一反应是网络，第二反应是代理。登上 NAS 一看——四个容器的主进程三天前就死了，而巡检脚本从头到尾都在报"一切正常"。

🕳️ 死了三天才发现

时间线大概是这样的。那天下午，容器里的代理进程崩了，主进程直接退出。

按理说 docker ps 该显示 Exited，但它没有。状态栏还是那个让人心安的 Up。

我的看门狗每五分钟探一次端口，端口一直是通的，于是每五分钟确认一次"健康"。这个循环持续了整整三天，三天里没有一条告警。

最后揭穿真相的不是监控系统，是我自己想用代理的那一刻。

🎭 端口在听，但不是它

复盘时最扎心的发现是：端口探活本身没有 bug，它只是探测错了对象。

容器崩了以后，宿主机上有个叫 docker-proxy 的用户态进程还活着。它独立于容器的生命周期，只要 Docker 守护进程不重启，它就一直替那个死掉的容器占着端口。

ss -tlnp 一看，端口确实在 LISTEN，但监听者是 docker-proxy，不是容器里的应用。

换句话说，看门狗一直在给一个尽职的替身演员鼓掌，正主早就退场了。

🔬 死活要对着两个视角看

真正能作证的，是 containerd 的视角。它和 Docker 各记各的账：

docker ps -q | wc -l
# Docker 视角：21 个容器

ctr -n moby task list | grep -c RUNNING
# containerd 视角：17 个真在跑

两边一对账，差出来的那几个就是假活。

处置也不复杂：对确认假活的容器逐个 docker restart -t 10，走正常重启流程基本都能救回来。但有一条禁令我写进了备忘——绝对不用重启整个 Docker 服务来自愈，那样不清残留，还会把旁边十几个健康容器一起拖下水。

之后我把看门狗升级了一版：以 containerd 的 task 状态和进程的挂载命名空间为铁证，端口探测降级成辅助信号。

💡 一点观察

监控最危险的失效方式，不是不报，而是它每五分钟都报一次——报一个它验证过的假象。探测本身也要被怀疑，尤其是那个"从来没红过"的指标。
