给 AI 发了一张文件通行证，我想了想又收回来了

2026-11-26 · MCPAI Agent · 约 3 分钟

之前写过《我是如何设计个人 AI Agent 的》，里面有个朴素的结论：AI 光会说话不够，得能动手。MCP 就是让它动手的那只手——一条把模型和外部工具接起来的标准协议。

之前写过《我是如何设计个人 AI Agent 的》，里面有个朴素的结论：AI 光会说话不够，得能动手。MCP 就是让它动手的那只手——一条把模型和外部工具接起来的标准协议。

但接上工具的那一刻，有个东西也悄悄接上了：风险面。这阵子折腾配置，记几条心得。

🔌 接线就两种方式

协议不复杂，接法就两种。本地走子进程：宿主按配置拉起一个进程当通道；远程走网络：填个服务地址加鉴权头。

配置核心是三件套：启动命令、参数、环境变量。示例长这样：

{
  "mcpServers": {
    "fs-tool": {
      "command": "npx",
      "args": ["some-fs-mcp"],
      "env": { "API_KEY": "${MY_TOKEN_FROM_ENV}" }
    }
  }
}

注意环境变量里引用而不是明文粘贴凭据——配置文件迟早会进版本管理或截图，凭据裸奔在里面是早晚的事。

🗂️ 它拥有它声明的权限

这是我想强调的一句：MCP 服务器拥有它声明的真实权限。挂一个文件系统 MCP，等于亲手递给模型一张文件通行证；挂数据库 MCP，等于把 SQL 执行权交出去。

所以每次挂载前，先想清楚「它到底要什么权限」：文件类只挂工作区目录，家目录绝不挂；数据库优先只读账号，写权限单独授权；代码仓库类用细粒度令牌，删除权限能不给就不给；涉及内部系统的，走网关加审计日志，凭据不过模型上下文。

另一个反直觉的经验：权限大的（shell、全盘文件）慎挂常驻，一次只挂当前任务需要的那几个，用完就移除。挂载列表越短，攻击面越小。

🕵️ 装之前读一眼

第三方 MCP 生态正在爆发，质量参差。我的规矩是：只挂官方出品或代码可读的，装前读一遍源码，重点看三样——有没有奇怪的外联请求、有没有收集凭据的动作、有没有诱导模型执行额外指令的痕迹。

还有一类风险更隐蔽：工具返回的内容会进入模型上下文，恶意网页或文件里埋的指令，可能顺着这个通道诱导模型去调用别的工具。防线只有一条——支付、删除、外发这类高危操作，永远要求人工确认。

💡 一点观察

给 AI 配权限，可以照着给新同事配权限的思路来：入职第一天，你不会把整栋楼的万能钥匙都给他。授权是信任的刻度，不是一次性的开关。
