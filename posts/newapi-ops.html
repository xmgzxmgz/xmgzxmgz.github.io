测试绿灯，调用红灯：自建中转站第一课

2026-11-26 · LLM 网关运维 · 约 3 分钟

自建中转站的第一个月，我学会最重要的一课：后台测试一路绿灯，实际调用照样可以一片红。

自建中转站的第一个月，我学会最重要的一课：后台测试一路绿灯，实际调用照样可以一片红。

🐳 四张表

这类自建网关的运维，说复杂也复杂，说简单也就是四张表的事。

渠道表管上游怎么接：官方、云厂商、其他中转、本地推理，各填各的。令牌表管下游怎么发：按工具或项目发独立令牌，配额度上限和可用模型范围，泄露时单独封禁不殃及全局。日志表管对账，用户表管额度。高频故障基本都出在前三张表的配合上。

🐳 三类故障

第一类：渠道测试通过，用户调用报 404。九成是模型映射没配——渠道里的模型列表管路由，模型重定向管改名，这是两个独立配置，改了列表不等于改了重定向。

第二类：流式输出中断或卡死。排查顺序固定：先看网关的代理缓冲设置（流式响应要关 buffering），再看超时时间，最后查上游限流。特征也很明显：直连正常、走中转必断，问题就在中间层。

第三类：额度对不上。去日志页拉消费明细逐条核对。有个容易忽略的坑：缓存 token 的计费倍率和普通 token 不一样，多模态输入里图片的换算也常有出入。更隐蔽的是上游涨价后没及时调自己的倍率——卖一份亏一份。之前写过一篇算 token 成本账的文章，账本意识是一样的。

🐳 例行功课

平时靠两条命令自检：

curl -s http://localhost:3000/api/status | python -m json.tool
curl -s -H "Authorization: Bearer $GATEWAY_TOKEN" \
  http://localhost:3000/v1/models | python -m json.tool

第一条看服务活着没，第二条用某个令牌查它实际可见的模型范围。

例行项归四件事：日志设保留天数，别让日志表膨胀拖慢后台；每周把所有渠道测试跑一遍，上游悄悄换端点能及时发现；数据库定期备份，配置丢失后重建成本极高；升级前看变更说明，备份数据库再拉新镜像。

还有一条底线：只要对外暴露，默认会话密钥必须改，注册要么审核要么关掉，管理后台走内网。上游密钥泄露，等于把钱包交出去。

💡 一点观察

中转站运维没有高深技术，拼的是「别相信单点验证」——测试绿灯只是第一关，真实的调用、真实的账单，才是系统的真相。
