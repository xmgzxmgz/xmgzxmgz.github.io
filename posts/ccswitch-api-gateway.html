一个 401，让我把换模型做成了换配置

2026-11-26 · LLM 网关排错 · 约 3 分钟

那天下午我的编码 CLI 突然全线 401，报错末尾还挂着一句「你好」。查到最后发现，错的不是我的密钥，而是链路上有一环悄悄过时了。

那天下午我的编码 CLI 突然全线 401，报错末尾还挂着一句「你好」。查到最后发现，错的不是我的密钥，而是链路上有一环悄悄过时了。

🐳 先说事故

现象很怪：CLI 走本地反代调用上游，所有模型一律 401。先怀疑密钥过期，登录态刷新过，文件时间戳是新的，重启也不解决。

顺着链路一跳一跳查：CLI 到本地代理正常，代理到转换器正常，转换器到上游网关——401。看日志才发现，最后一次成功请求停在十几天前。

根因有点哭笑不得：上游桌面客户端某次更新，把凭据文件里的令牌从明文改成了加密信封。链路上那个小小的转换器没有解密逻辑，把整个加密信封原样塞进请求头发了出去。网关看到一串乱码，当然回 401。至于「你好」，那只是 CLI 给会话起标题的小请求，跟着一起 401 而已。

这件事的教训：401 不一定是「你的 key 错了」，可能是链路中间有人在转发它看不懂的东西。

🐳 为什么要网关

出事之前，我的供应商配置是散装的：每个工具各存一份地址和密钥，供应商一换全要改一遍。后来我搭了一层本地网关：所有应用只认本地地址，供应商信息全部收进网关的配置文件里。好处有三条——应用代码零改动；所有请求过网关，用量和失败率一处可查；换供应商变成换配置。

🐳 配置即切换

档案化的配置大概长这样：

profiles:
  daily:      # 便宜渠道，日常跑
    base_url: http://localhost:8080/v1
    api_key: ${DAILY_KEY}
  official:   # 高端模型才走
    base_url: http://localhost:8080/v1
    api_key: ${OFFICIAL_KEY}
routing:
  default: daily
  fallback: [official]

日常手动一条命令切换，长期挂机的服务配健康检查自动落备用。有个细节值得记：探测别用模型列表接口，用最小请求去探，那才反映推理通道的真实可用性；连续失败几次才切换，避免抖动。

那场 401 之后我又庆幸了一次：配置收在一处，排查链路只有几跳，临时切备用只要一条命令。

💡 一点观察

把「换模型」从改代码变成改配置，本质是把易变的东西和稳定的东西分开——模型和供应商永远在变，你的工作流不该陪着他们一起动。
