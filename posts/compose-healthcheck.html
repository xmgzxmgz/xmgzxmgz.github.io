depends_on 只管启动，不管活没活

2026-11-26 · dockercompose · 约 3 分钟

有一回我的应用容器起来了，日志却满屏连接数据库失败。我盯着 compose 文件里的 depends_on 发呆：不是写了依赖吗？

后来才明白，depends_on 只保证「数据库容器先启动」，不保证「数据库已经就绪」。启动顺序和真能干活，是两码事。

📋 规范是写给半年后的自己

先说 compose 文件本身的纪律，我吃过的亏都在这上面。

镜像 tag 禁止用 latest。当年全写 latest，半年后想升级，pull 下来一堆不兼容变更，根本不知道原来跑的是哪个版本。tag 固定到具体版本号，升级才是显式动作，而不是重启时的意外。

数据一律显式挂载命名卷。容器删了，写在容器层里的东西就没了，这是设计，不是 bug。

一个项目一个目录一个 compose 文件，散落的 docker run 三个月后没人记得带过什么参数。

🩺 健康检查探的是「能干活」

回到开头的问题，真正的解法是给服务配 healthcheck，再让依赖方用 condition: service_healthy 等待：

healthcheck:
  test: ["CMD-SHELL", "pg_isready -U postgres"]
  interval: 10s
  retries: 5
  start_period: 30s

这里最容易踩的坑是「探什么」。进程活着不等于服务能用，HTTP 服务要探关键端点，数据库用原生的就绪命令，别拿「进程存在」糊弄。

另一个坑是 start_period：要建表、加载模型的服务启动本来就慢，不给宽限期会被误判成不健康，反复重启，越重启越起不来。

🔄 升级要有回头路

compose 写规范了，升级就简单：改 tag，pull，up -d，跟着 logs 观察。有问题把 tag 改回去重建，一步回滚。

但数据库是例外：schema 迁移是单向门，新版本改了表结构，旧版本程序未必认，回滚常常不成立。所以数据库升级前，除了打数据卷快照，还要先读 release note 的迁移说明。

单机 compose 下，不健康的容器只是被标记，不会自动替换，想闭环还得靠外部看门狗补一只手。

💡 一点观察

compose 文件不是配置，是给未来的自己留的说明书。写的时候多花十分钟，半年后排查故障时会少熬一个通宵。
