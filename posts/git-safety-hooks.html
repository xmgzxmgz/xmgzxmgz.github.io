git 里最不该出现的东西，我让钩子替我拦

2026-11-26 · git安全 · 约 3 分钟

每个用过 git 的人心里都有几条红线：密钥不能进仓库、没审过的东西不能 push、reset --hard 前要看清楚。问题是，红线靠记，而记忆在赶时间的时候最不可靠。我后来想通了：守不住的纪律，就写进钩子里。

每个用过 git 的人心里都有几条红线：密钥不能进仓库、没审过的东西不能 push、reset --hard 前要看清楚。问题是，红线靠记，而记忆在赶时间的时候最不可靠。我后来想通了：守不住的纪律，就写进钩子里。

🐳 自觉是种概率

靠自觉守纪律的结局可以预测：九十九次都守住了，第一百次深夜赶工，顺手一个 git add . 加 git push，密钥进了历史。

而 git 的历史是赖账的——文件删了，提交记录里还在，仓库只要被克隆过一次，就算彻底出去了。敏感信息入库不是「清理」能解决的问题，是只能在入口处拦的问题。

于是我把红线分成三层：commit 前拦敏感信息，push 前拦未授权推送，高危命令在本地做二次确认。

🐳 pre-commit 当门卫

pre-commit 钩子的核心逻辑不复杂，对着暂存区的 diff 做模式匹配，命中就拦：

PATTERN='(sk-[A-Za-z0-9]{20,}|BEGIN (RSA|OPENSSH) PRIVATE KEY)'
git diff --cached -U0 | grep -Ein "$PATTERN" && exit 1

除了密钥形状，我也会拦隐私文件名，比如 .env、.pem 这类文件压根不该有进仓库的机会。真有误报，--no-verify 可以绕过，但那条路是有意的摩擦——绕过的人必须知道自己绕过了什么。

钩子文件默认不随仓库走，配一句 git config core.hooksPath hooks，把钩子当源码放进仓库统一分发，每台机器一条命令生效。

🐳 push 之前多问一句

pre-push 我做成「白名单放行、其余确认」：个人知识库这类预授权仓库直接过，其他仓库一律先打印目标地址，问一句确认再推。

高危命令是另一层。reset --hard 丢掉的提交其实还能在 reflog 里捞回来，真正的无底洞是 clean——未跟踪文件被清了就是真没了。所以我给危险别名内置了确认，clean 这种操作永远要多按一次 y。

工具的办法说白了就一句话：让正确的事情容易做，让错误的事情做不成。

💡 一点观察

纪律和工程的区别，大概就是前者依赖当时的你，后者依赖提前设计好的系统。深夜的自己不值得信任，这一点越早承认越好。
