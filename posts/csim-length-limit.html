AT+CSIM 的 8 字节魔咒

2026-09-18 · eSIM 排查 · 约 2 分钟

我一度得出「这块模块物理上无法读取 eUICC」的结论，还写进了文档。这个结论是错的，错得很有教育意义。

CellPort 系列：我为一块大疆定制 4G 模块（实为移远 EG25-G）写的 Windows 管理工具，对标 macOS 上的 CellDock。本篇是一个差点写进文档的错误结论。

开发初期我测过一组数据，并据此下了结论：这块模块固件的 AT+CSIM 透传有约 8 字节的 APDU 长度上限，因此物理上无法进入 ISD-R，eUICC 管理没戏。实测数据看起来非常扎实：

APDU长度结果
SELECT MF 00A40000023F007 字节9000 成功
同上补 1 字节8 字节612E（已执行）
同上补 2 字节9 字节无任何响应
SELECT AID（16 字节）21 字节无任何响应

💡 转折：换一条路，而不是硬闯

后来发现 SELECT ISD-R 本来就不该走 CSIM。3GPP TS 27.007 定义了逻辑通道指令，让模块固件内部完成 ISD-R 选择：

AT+CCHO="<ISD-R AID>"   → 固件内部选择，返回通道号
AT+CGLA=<ch>,<len>,"<hex>"   → 在通道上透传 APDU
AT+CCHC=<ch>                → 关闭通道

这套指令固件全部支持。最终基于它实现了完整的 ES10c 客户端：7 个 Profile 全部读出，启用/停用切卡往返实测成功。

🪞 复盘

「无响应」不等于「不支持」，也可能意味着「这条路本来就不该走」。当你得出的结论是「物理上不可能」时，先去找找有没有另一扇门，再考虑把结论写进文档。

那个错误的结论后来从文档里删掉了，但测试数据保留了——它记录的是一条死路的位置，对后来者同样有价值。
