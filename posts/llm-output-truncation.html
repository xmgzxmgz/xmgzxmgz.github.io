回答写一半就断，先别怪网络

2026-11-26 · LLM排错 · 约 2 分钟

让模型写篇长综述，写到一半戛然而止，JSON 都没闭合。第一反应是网络抖了，重试三次才想起来：先看看它是怎么「死」的。

🐳 先看哨兵

每次响应里都藏着一个哨兵字段：finish_reason。它没说出口的话，比报错信息诚实得多。

length，顶到了 max_tokens 上限被硬切；stop，正常结束，如果内容明显没写完却给了 stop，要查安全过滤；tool_calls，模型在等工具结果回填，根本不是截断；至于没有这个字段、连接直接断掉，那才是网络或网关层的事故。

一个最小诊断请求：

curl -s http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" -d '{
  "model": "gpt-5", "max_tokens": 16000,
  "messages": [{"role":"user","content":"写一篇 8000 字综述"}]
}' | python -c "import json,sys
print(json.load(sys.stdin)['choices'][0]['finish_reason'])"

第一步永远是读它，别猜。

🐳 三层嫌疑

截断的嫌疑犯分三层。

第一层是参数：模型输出上限就那么大，或者你把 max_tokens 设小了。第二层是网关：很多中转站会「好心」把 max_tokens 往下压，或对单次响应体有独立大小限制——特征是官方直连好好的，一走中转必断。第三层是流式：SSE 长连接被中间层缓冲或切断，修法是网关侧关缓冲，客户端做断点续传。

最坑的是第二层：参数调到天上去也没用，限制根本不在我这头。

🐳 分段的艺术

后来我不再和 max_tokens 搏斗，改了生成结构。

先大纲后分段：第一次调用只要大纲，之后逐节展开，每节输出上限各自独立，一段断了重试一段。续写协议：每段结尾放个标记，客户端看到就发「从上段结尾继续」。要结构化数据时用 JSON Lines，一行一个独立对象，断了只丢一行，不丢整篇。

最后加一道校验：客户端解析失败就自动触发续写重试，不把残缺结果往下传。

💡 一点观察

截断不是 bug，是约束。把长任务设计成多段短输出加确定性拼接，比祈祷任何一次超长输出完整落地都可靠。
